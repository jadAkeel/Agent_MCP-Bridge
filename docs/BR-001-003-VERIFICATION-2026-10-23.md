## BR-001 — requeue idempotency collision

**Confirmed cause:** the key helper stripped every trailing `:requeue:<n>` even from an original user key. A root ending in `:requeue:1` therefore generated its own key on the first retry. Normal request deduplication returned the predecessor; the receipt writer allowed a self-successor.

**Changes:**

- `lib/queue.js`: remove only the final suffix matching a persisted retry's `requeuedFrom` / `requeueSequence`. Preserve suffixes in the original user root, deterministic keys, and the existing 200-character bound.
- `lib/queue/retry.js`: pass persisted lineage to the helper; refuse a self-successor receipt.
- `server.js`: a retry deduplication hit must match both its predecessor and sequence. An unrelated row holding the same derived key is an idempotency conflict, not a successor.
- `tests/review-queue-features.js`: normal/suffix/nested-suffix roots, three successive retries, concurrent callers, repeated admission after a missing predecessor receipt, unrelated-key occupancy, self-mark refusal, and automatic same-model retries stopping at `maxAttempts`.

**Before fix:** the added suffix-root regression failed because the successor equalled its predecessor (34/35 tests passed). Normal control and existing concurrency coverage passed. **After fix:** 37/37 passed, including four executions for each manual three-retry chain and exactly three executions for the automatic three-attempt policy. No retry eligibility, model allowlist, scope validation or execution-budget policy was broadened. The old helper assertion retains its expected output and now supplies the lineage of the retry it represents.

Existing corrupted historical self-receipts are not migrated or rewritten by this fix. An unrelated job deliberately occupying a derived key is refused rather than silently linked or rerun.

## BR-003 — late SQLite contention and duplicate attestation

**Confirmed cause:** the five-second SQLite retry deadline started before waiting on a live owner. A transient lock encountered after that healthy wait exhausted an unrelated budget and immediately fell back to another fresh operation.

**Changes:**

- `lib/attestation-cache.js`: start the existing five-second contention window on the first SQLite busy/locked error, and reset it after a successful database poll. Bound the entire claim/owner wait by the existing flight-lease duration (default ten minutes), so repeated successful polls cannot extend waiting indefinitely. Expiry/error still falls back to the original fresh policy-checking operation. TTL, fingerprint checks, positive-only caching and publication ownership checks remain intact.
- `tests/review-shared-attestation.js`: barriers ensure a real SQLite owner claim and one successful follower poll precede injection. Advance the test clock by 5.2 seconds at the next poll, inject `SQLITE_BUSY`, and release the owner after the failure is processed. Cases cover successful owner sharing with zero follower operations, owner refusal, owner exception, follower-input drift, persistent locks exhausting their budget, and owner-wait expiry. Built-in prototype/clock modifications are restored in `finally`. The existing real-process 15-second sharing and byte-drift tests also pass.

**Before fix:** late-success regression returned `fresh`, not `shared`; the persistent-lock test observed only one attempt, exposing immediate fallback (33/35). **After fix:** 35/35 passed, zero skips. The regression uses deterministic clock advancement and injected SQLite errors, not a claim that it held a physical SQLite lock for 5.2 wall-clock seconds. Existing real multiprocess/SQLite integration coverage was also executed.

This proves correction of the diagnosed follower-acquisition mechanism. It does **not** establish the unlogged exception behind historical CI, guarantee sharing when the optional cache cannot publish, or permit stale attestations after input/policy changes. Persistent storage errors and exhausted waits intentionally still perform fresh checks.
